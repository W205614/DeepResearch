# 2026-10-25 改善与证据边界

本轮修复现有研究流程的两个问题：证据仍有缺口时，补查可能因为主题已经搜索过而返回空查询；最终覆盖检查没有收到分析缺口，可能把缺少用户明确要求的具体事实判为完整回答。修改仅在 `ResearchGraph.reflect` 的查询细化提示和 `ResearchGraph.validator` 的覆盖输入/提示，不增加 Agent、搜索上限或重试层。

最终覆盖仍是模型判断，不保证完全正确。`gaps` 仅作为核对线索，并不直接把所有局限判成失败；用户只问“资料是否提供某信息”时，范围明确的未知说明可以回答问题。格式核验不完整仍保留草稿并阻止送审；部分报告的异人批准仍须说明发布范围。

## 效果输入与结果

开发问题取自 Python pathlib 与 HTTPX；按来源独立的留出问题取自 SQLite 与 PostgreSQL 17。题目、原文片段、逐题预期事实和禁止结论在真实调用前冻结，见 `source-independent-cases.json` 与 `frozen-contract.json`。开发结果用于修复，留出输出未用于后续调参。

这是**真实模型、冻结并分阶段开放检索片段**的机制对照：首次检索仅返回首段，真正进入补搜后可取得剩余片段。每个配置只执行一次，不选最好一次；它只验证可控证据缺口下补搜的作用，不证明真实联网搜索或一般业务准确率。

| 留出问题 | 不补搜覆盖 | 有界补搜覆盖 | 两配置引用支持 | 结果范围 |
| --- | --- | --- | --- | --- |
| SQLite 连接隔离与 WAL | 2/4，50% | 4/4，100% | 均100% | 当前模型、固定片段、单次成对运行 |
| PostgreSQL 17 隔离快照 | 3/4，75% | 4/4，100% | 均100% | 报告先生成，终评在获准阶段调剂后补完 |

PostgreSQL 的首轮终评在留出阶段40次 HTTP上限前被阻止，保留了暂停记录。协调方随后明确批准将保存报告阶段56→48、留出40→48，模型总160次、token与其他供应商总上限均不变；只对现有报告及引用追加2次终评，没有重新生成或改变评分规则。授权及账本修订哈希可追溯，见 `budget-transfer.json`。

两个开发样本的首次机制对照没有改善覆盖；修复后的保存状态组件复核分别生成4个新查询，并把未解决请求保持为非完整回答。它们不是修复后的全新研究通过证据。最初 URL 片段适配错误造成的失败、已用请求及修订记录均保留，不能从总消耗或失败分母删除。

## 六题历史缺口

ConfigMap、Pod lifecycle、Quota、StatefulSet、Probes、Secret 的保存报告已完成本轮组件闭环。Pod 精确复用了已付费修订；ConfigMap、Pod、Quota 的变化结论重新核验，StatefulSet 来源展开变化后对全部15条重新评分。其余精确相同的可支持结论按完整引用对象匹配后复用历史评分；历史配置证据不完整的限制仍保留。

六题的混合支持和本轮预期事实覆盖均为100%，但**不能写成六题全新端到端通过、60题当前模型全过或全新独立评分**。保存报告阶段使用修复前覆盖提示；ConfigMap、Secret 的生产覆盖判断仍为非完整，按部分结果保留，不升级为完整正式报告。历史 `research-evidence-status.json` 是2026-10-20快照，原记录不覆盖；本轮结果另列于 `delivery.json`。

## 重排取舍

分析原50查询逐条结果，重排只在 `public-probes` 改善 nDCG@5：目标资料从第二位到第一位；其余49题该指标不变，没有下降。Recall@5维持98%，总体 nDCG@5为96.52%→97.26%，历史冷查询P95新增511.56ms。没有为凑指标改算法或重新收费跑全量。超时、HTTP异常、无效索引/分数、重复结果、外发限制、缓存契约和融合回退通过聚焦测试。重排仍是可选取舍，不代表最终报告准确率提升。

## 实际体验与恢复

三角色真实浏览器、OIDC、后端、数据库完成资料版本、影响、修订、差异、自审禁止、异人发布和权限撤销；该轮模型为确定性夹具。另一个正常内部研究使用真实供应商生成，核对800元、实习生不适用、资料引用及 Markdown下载，随后从保存报告实际打开原文。检索嵌入为固定夹具，界面保留部分结果状态，不是完整真实嵌入质量证明。

真实模型证据不足场景在浏览器阶段16次调用上限后停止，未计通过；零供应商调用的独立夹具补验了证据不足说明及阻止送审。首次共享 Windows/Linux SQLite账本发生存储错误，后将完整既有账本移到容器本地卷，合并前逐行验证原记录前缀，未清零已用额度。全部失败记录保留。

当前数据/配置/镜像/ClamAV备份全量校验通过；同机隔离恢复14个存储项、双数据库、账号权限、正式报告正文和引用哈希、授权检索、离线正常文件/EICAR扫描，以及接单后取消。恢复约128.58秒，不代表异机灾备或 SLA。

三个日常Python服务重建后源码指纹一致，选定业务逻辑表哈希和原挂载保持，资料13、会话22、任务45、正式报告1、成员关系10、空间8、账号3。验收后恢复22个日常容器全部停止。临时验收数据与账本先归档，再按明确清单清理；业务卷、匿名监控卷、回滚镜像和历史恢复材料保留。

## 预算、CI与可复用材料

`scripts/bounded_evaluation.py` 只在显式运行时安装 HTTP记账钩子：在传输前持久预留，所有重试累计；缺失 usage 保留保守预留，身份/余额/限流或上游错误停止后续调用。报告区分实际 token、未知使用量的保守预留和请求数量，不推算人民币费用。CI四个原有评测步骤共用一个账本，题目、断言及阈值保持不变。

最终提交自身 SHA不写回源码；Answer Quality工作流生成绑定 `GITHUB_SHA` 的 `delivery.json` 回执并上传 artifact。其他 CI、安全门禁仍需对同一 SHA独立核对。没有人工盲评、真实外部用户反馈、HA、生产容量或通用准确率证明。

本地只执行直接相关的8项图片/PDF/DOCX测试、证书加载、真实浏览器报告净化1项及前端构建。DOMPurify公告涉及特定配置，不据此断言本项目当前配置已被利用。

安全补丁随后重建三个Python服务与Web。实际容器包版本和三个容器内锁文件已核对；新Web包内确认DOMPurify 3.4.17并再次仅验证净化路径。实际Linux镜像通过PNG、含图像扫描PDF及证书加载；首次空白PDF探针因无内容返回空列表，失败记录保留后仅更换无效夹具。原业务表哈希、精确持久挂载及30个其他项目容器保持，22日常容器恢复停止。新的升级前备份完成校验；隔离恢复证据沿用同日业务数据一致的演练，不声称本次又完成了一次恢复。
