# 证据生命周期：开发计划与验收边界

本轮把项目主线推进为“资料版本变化 → 报告影响识别 → 受控修订 → 异人审核 → 冻结交付”。目标是可维护的个人单机项目。多租户商业化、高可用、多地域容灾和无限规模检索不在本轮交付范围。

## 开发阶段与停止扩建标准

| 阶段 | 实现内容 | 停止标准 |
| --- | --- | --- |
| 1. 版本与证据 | 保留文档版本、结构化块与片段快照；事务切换当前版本；资料变更事件与 corpus revision | 索引失败旧版本可用；旧来源可追溯；并发切换不会把待发布片段当成当前来源；历史缺失明确标记 |
| 2. 影响与修订 | 冻结需求、结论与来源；影响清单；报告系列；定向修订和完整研究回退 | 重复修订请求只创建一次；过期任务不能覆盖新结果；来源变化能阻止旧报告提交和批准；原正式报告正文与引用不变 |
| 3. 实际使用 | 文档版本差异、受影响结论、修订进度、报告差异与当前版本入口 | 作者、异人审核者、只读者完成浏览器闭环；越权操作受服务端限制；切换空间不显示前一空间异步结果 |
| 4. 稳定与恢复 | 有界查询与下载；Outbox/租约恢复；独立告警转发；一致性备份与隔离恢复 | Worker 重启不重复完成；Redis 恢复后投递可继续；Milvus 故障有关键词回退；Agent 停止仍能接收告警；恢复副本验证账号、权限、正式报告 SHA 与引用、检索和接单 |
| 5. 质量与交付 | 扩大固定集、真实嵌入/重排/模型评测；30 分钟受控运行；文档与最终 CI | 原有固定门禁保持原阈值；扩展题不删题、不改阈值，明确记录未完成项；重排不损失融合召回且排序收益及新增延迟符合脚本门槛，否则关闭可选重排；最终提交 CI、安全与回答门禁通过 |

停止扩建的含义是上述闭环与关键边界都有可复现证据，失败可定位恢复，受控运行没有未处理错误。其后只修实际缺陷、依赖安全问题与有证据的瓶颈。30 分钟运行和固定集通过不构成长期 SLA；随机生成模型也不能通过有限测试证明永远正确。

本轮持续运行采用明确判据：连续接单1800秒，停止接单后180秒内全部收敛；所有接单研究完成、所有接收的资料版本索引就绪，无未处理错误。至少出现一次索引完成时同样两个研究任务仍处于真实running状态，并实际跨越访问令牌到期、经正常客户端续期。受监测的8个核心服务没有OOM或非预期重启。主动中止、超时或只跑了部分时长均不能算通过。该工作负载是低并发组件验证，不据此宣称生产吞吐量。

真实模型门槛沿用评测脚本：关键用例全部通过，整体通过率至少85%、引用支持率至少95%、需求覆盖率至少85%；保留失败及未完成项。正文、来源、结论和评分输入完全相同且可核对哈希时可以引用旧评分，但须标明复用范围和历史配置记录的限制；协议适配的离线兼容检查不能冒充重新调用新协议。

2026-10-20，在有上限的本地真实模型补验后，用户确认停止继续付费，保留扩展集6题待验，按功能、角色、恢复、完整混合运行及原有最终CI交付。这是对本轮扩展质量门槛的明确调整：原CI的题集与阈值不变，扩展60题不作为已全部通过的阻塞门禁，也不计算缺失项为通过。已知历史内容缺陷和未完成的修订仍在[交付记录](lifecycle-delivery-20261020.md)与[结构化证据状态](../eval/lifecycle/research-evidence-status.json)中列明，不为凑通过率反复抽取最好的一次。

## 关键实现

- Python 以事务保存当前资料版本与变更事件；影响处理可重试。Milvus 负责候选召回，PostgreSQL 决定当前有效来源。关键词与重排输入包含有界标题和定位信息，原文不被重写。
- 每次研究冻结需求、结论、来源及资料修订号。Java 在提交及批准时重新验证资料修订、源文档版本、任务 attempt 与系列当前版本。公共研究使用独立的范围标记，避免被内部资料更新误伤。
- 定向修订仅在旧引用文档被替换且其余证据仍有效时使用；新增、删除、未知历史等情形回退完整研究。复用结论仍经过核验与需求覆盖检查。
- 发布创建不可变快照；系列当前指针经过比较更新。撤回保留历史，不自动把旧版恢复为当前版。修订幂等键与普通研究请求隔离。
- 核验使用程序提供的完整结论原文与目标编号，模型只返回编号对应的判断，程序负责逐结论原文绑定，避免用来源中的正确改写替代待核验断言。编号缺失、重复或未知属于核验未完成，保留草稿并阻止提交，不把格式错误当成事实错误删除内容；只有完整的语义核验发现不支持或遗漏必要条件时才执行一次修复。规则与交互协议带版本；旧缓存、旧检查点及旧待审结果不能跳过当前规则直接完成或发布，已发布历史仍保留原快照。
- 告警转发独立于 Agent 进程，使用内部令牌、有界请求、重试及去重。真正的外部通知还需配置接收地址；本轮演练使用隔离录制器。

## 本机端口持久配置

当前维护机器的 `.env` 设置 `APP_PORT=8080`，`COMPOSE_FILE=compose.yaml;.env.local-ports.compose.yaml`；覆盖文件保留 Web 8080、Keycloak 8480 及匹配 CSP/hostname。另一个项目继续使用 8380。这些带本机信息的文件不提交仓库。

已有 Keycloak 数据不会因修改导入 JSON 自动更新客户端。服务启动后执行：

```powershell
uv run python scripts/configure_local_oidc.py --web http://localhost:8080 --identity http://localhost:8480
```

脚本先核对所选 Compose 服务实际发布端口，再更新现有 `deepresearch-web` 的回调与 Web Origins。其他部署使用自己的真实端口和 CSP；不要复制本机覆盖文件到不相关项目。

## 隔离验收与恢复

隔离环境使用项目名 `dr-lifecycle-acceptance`、Web 28080、OIDC 18480 与独立数据卷。浏览器流程使用确定性测试模型，验证真实身份、权限、数据库、索引与业务状态机；真实模型质量另行评测，不能混为一项证明。

```powershell
uv run python scripts/prepare_lifecycle_acceptance.py
docker compose -f compose.yaml -f compose.acceptance.yaml -p dr-lifecycle-acceptance up -d --build --wait --wait-timeout 300
```

该覆盖文件包含专用私网段，端口和网段使用前应核对本机占用。不要为获取空闲网段清理其他项目网络。

运行浏览器套件时同时指定实际入口、身份入口与项目名；测试启动器会核对发布端口。日常本机身份入口为 8480 时，`E2E_KEYCLOAK_BASE_URL` 也必须设置为 `http://127.0.0.1:8480`，不能沿用 CI 的默认 8180。故障与持续运行套件仅接受隔离项目，避免误操作日常服务。

备份会短暂停止所选项目，归档卷、镜像和私有部署快照，最后恢复原先运行的服务。目录含业务数据和密钥，应保留在本地：

```powershell
uv run python scripts/recovery.py backup --path .cache/recovery-lifecycle-20261020-01 --compose-file compose.yaml --compose-file compose.acceptance.yaml --source-project dr-lifecycle-acceptance
uv run python .cache/recovery-lifecycle-20261020-01/restore.py restore --path .cache/recovery-lifecycle-20261020-01 --project dr-restore-lifecycle-20261020-01 --subnet 10.254.245.0/24
```

恢复要求新的项目名、空的新卷和不重叠网段；先验证归档和镜像哈希，再创建资源。恢复使用快照中的脚本、镜像与只读绑定副本，禁止覆盖原卷。验证包括实际 OIDC、权限撤销、正式报告正文/证据 SHA、当前文档检索及研究接单后取消；上游模型关闭，不宣称恢复后已完成真实模型研究。结束仅移除本次恢复容器，保留卷与结果清单。

本轮仅在同一台机器隔离恢复，不属于跨主机灾备。当前代码与测试证据会在最终交付记录中标明执行结果；操作说明本身不是通过证据。

## 扩展检索实测

2026-10-20，30 份当前资料实际形成 632 个片段，50 个文档相关性查询；真实 `text-embedding-3-large` 与配置的 HTTP 重排服务。三种方法使用同一资料集与标注：

| 方法 | Recall@5 | nDCG@5 | MRR@10 | 冷查询 P95 |
| --- | --- | --- | --- | --- |
| 仅向量 | 88.00% | 81.51% | 80.37% | 2076.64 ms |
| 关键词与向量融合 | 98.00% | 96.52% | 96.00% | 2548.39 ms |
| 融合后重排 | 98.00% | 97.26% | 97.00% | 3059.95 ms |

重排相对融合新增 P95 511.56 ms，通过当前脚本的不降召回、排序收益及新增 P95 ≤ 2000 ms 门槛。原有小题集结果不被替换；扩展结果也不能推广为所有资料的准确率。40 个制度问题来自两个模板，同源公开资料占其余 10 题，存在模板与来源偏差。

本轮先前结果未通过后进行了通用修复：数字核验允许合法空白与千位分隔，仍区分单位及不同数值；长中文证据按问题相关性选窗；检索输入补充标题与定位；核验把完整结论作为保守目标绑定原文，要求其全部内容获支持，任何不支持内容或遗漏必要条件均阻止整体通过。当前实现没有进行确定性的语义子命题拆解，模型的判断仍可能出错。失败日志保存在本地，未降低通过阈值。

另发现冻结原始 Markdown 没有展开官方定义宏，却要求回答其中定义的评测前提问题。研究证据现补齐相同上游提交的定义依赖并记录哈希；原始检索资料与抽样输入保留不变，避免把输入版本变化伪装为算法收益。详见资料集说明与保留的失败记录。

可提交的汇总见 [`eval/lifecycle/retrieval-results.json`](../eval/lifecycle/retrieval-results.json)。评测发生在提交前的修改工作区，记录的旧 HEAD 只是当时 checkout；不等于旧提交已经包含本轮代码。研究评测另记录 backend 源码指纹和工作区状态，恢复备份绑定实际镜像 ID，并分别记录 checkout SHA 与 dirty 状态。
