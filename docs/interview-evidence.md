# 面试证据与源码入口

本文是可核查材料，不证明开发者已经掌握口头讲解或现场编码。

## 一次请求如何完成

浏览器通过 Keycloak 授权码和 PKCE 获取身份 → API 校验工作空间成员权限 → `Runtime.create` 在工作空间锁内先查请求编号，再校验额度和内容 → PostgreSQL 保存任务 → Redis 使用稳定任务编号投递 → Worker 领取并增加尝试版本 → 研究图恢复检查点并执行各节点 → 当前版本才能提交终态 → SSE 按持久化事件编号重放，前端读取报告和引用。

源码入口：[runtime.py](../backend/services/runtime.py)、[graph.py](../backend/research/graph.py)、[worker.py](../backend/worker.py)、[enterprise.e2e.ts](../frontend/e2e/enterprise.e2e.ts)。

## 可以现场解释的故障案例

| 触发 | 修复前风险 | 当前行为与证据 |
| --- | --- | --- |
| 上传开始索引时删除 | 迟到向量/SQL 写入令资料复活 | 资料版本作废，发布时重新检查版本；检索只接受当前 SQL chunk；真实 Milvus 验证无残留。见 documents.py、test_components.py |
| 队列满时重试同一请求 | 先检查额度导致原请求也被拒绝 | 先返回匹配原任务，修改内容则冲突；SQLite/PostgreSQL 统一业务异常。见 test_consistency.py |
| 同时多次调用搜索 | 并发检查越过额度，删除研究返还次数 | 事务原子预占任务和 UTC 日额度，任一失败全部回滚；独立台账不随研究删除。见 postgres.py、0004_consistency.py |
| Worker 被终止，旧进程迟到 | 重复执行或覆盖新结果 | 心跳/终态带尝试版本；持久化任务对账补投；52.44 秒恢复、单个 done。见 verify_components.py |
| Redis 投递失败 | 数据库已接受但队列无任务 | 接受记录留在数据库，周期扫描补投，稳定队列编号去重；真实 Redis 停启通过 |
| 报告把“未完成 42 人”写成“完成 42 人” | 关键词相同而错误放行 | 独立支持判定覆盖否定、主体、日期及范围；固定错误反例必须拒绝。见 quality_gate.py、evaluate_answers.py |

## 设计取舍

1. SQL 是任务和资料有效性的权威，向量库负责候选检索。跨数据库无法一次事务提交，采用版本校验与补偿清理；这增加清理状态，但避免依赖分布式事务。
2. 采用持久化任务表对账和 Redis 去重，未引入新消息中间件。保证旧尝试不能提交最终结果，不承诺模型外部调用恰好一次；故障窗口可能重复调用并消耗额度。
3. 幂等语义绑定工作空间、请求编号及请求内容。它解决重试，不能替代权限验证或无限制恢复。
4. 质量阈值依赖版本化小题集和模型辅助评分。前轮 30 题通过 29 题允许保留非关键过度拒答，修复相关证据裁决后最终本机 30/30；关键拒答、冲突、反注入全部必须通过。不能把这个分数写成通用行业准确率。
5. Compose 演练只证明单机可恢复。备份恢复 202.05 秒是本次测量，不是恢复服务承诺。

数字、执行命令与失败记录见 [收尾验收](interview-delivery.md)。面试时可从上述任一故障解释：哪个状态是权威、在哪里检查版本、失败后谁来补偿、测试如何制造竞争、仍有哪些不能保证的边界。
