# 多团队共用验收与实施计划

适用于多个团队分别使用各自工作空间、共享部署和供应商账户的场景。首先用两个隔离工作空间复现真实入口的行为，再据结果修复。每个阶段记录源码提交、应用镜像摘要、配置、失败证据和复测结果。

## 已有基础

- 平台管理员可转交空间所有权、停用和恢复账号。转交保留历史作者，停用和恢复使旧令牌失效。资料检索和报告按工作空间、角色及当前资料授权判断。[治理集成测试](../business-backend/src/test/java/com/deepresearch/business/PlatformGovernanceIntegrationTest.java)
- 已有测试覆盖资料撤权后旧任务、历史报告、事件流、批量报告下载及原始证据的读取边界。撤权控制后续读取，已下载的文件由组织另行管理。[资料授权测试](../tests/test_document_acl.py)
- 已有工作空间执行并发上限及平台、空间、供应商账号的模型额度账本。当前待处理队列有全平台上限，仍需实测单个空间持续提交时其他空间的准入和等待行为。[调度准入](../business-backend/src/main/java/com/deepresearch/business/service/ResearchCommandService.java) · [额度测试](../tests/test_usage_governance.py)

## 先验证撤权

1. 建立 A、B 两个工作空间及所有者、协作者和旁观者。上传带唯一标记的合成资料，生成可搜索条目、带引用的历史草稿和经独立审核的正式报告。预热检索和报告读取路径。
2. 先记录授权账号可见内容，再通过正常管理接口撤销其授权和执行一次所有者交接。用原会话复查关键词与向量检索、历史报告正文与引用跳转、正式报告以及单项和批量导出。补测已打开的事件流和正在导出的请求。保留授权的成员应继续使用对应资料。
3. 每个用例都验证受限资料的标记、标题、正文及下载入口是否泄露，同时检查历史作者和有权成员可见的报告未被修改。发现失败时修复实际读写路径的授权检查，补一个可稳定重现的回归用例。

## 再验证队列与模型额度

1. 在独立 PostgreSQL、Redis 和 Worker 组成的栈中，使用固定模型响应和可控执行时长。测 B 单独运行的基线，再由 A 持续占用并发、堆积队列并耗尽其空间模型额度；B 以同样速率提交和执行，加入取消、重新投递、额度周期切换三个覆盖点。
2. 对每个空间记录接单成功率和拒绝码、队列等待 P95、完成率、按任务和空间记账的请求数与预占量。明确区分空间额度耗尽与共享平台或供应商账号额度耗尽。平台仍有容量时，验证 B 在约定等待时间内可接单和执行；共享硬上限耗尽时核对两组拒绝原因与账本。
3. 若 A 填满待处理队列导致 B 被拒绝，先在现有事务内增加工作空间待处理上限，保留平台总上限、任务幂等和恢复语义。若 B 能接单但持续超出等待预算，再基于测试证据评估按工作空间轮转。额度串账优先修复账本归属或原子预占。用同一套负载比较修复前后。

## 验收交付

- 发布测试报告，包含授权对照、并发和额度基线、峰值结果、失败原因与复测。撤权用例均须通过，公平性阈值按团队实际可接受的等待时间确定后固定到测试配置。
- 在同一提交跑完整 CI 和 Security。需要声明真实供应商吞吐或实际费用隔离时，再用获准的供应商账号及预算独立验收。
